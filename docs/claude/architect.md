# Architecture

Design from the project owner; the vault, browsing (step 2), its dual-pane UI, the basic file operations (step 3a) and the multipart transfer engine (4a) and the background transfer queue with its UI (4b) are implemented; view/edit is not yet.

- **Shell**: Tauri desktop app (Rust backend + web frontend).
- **UI**: Total Commander-style dual pane. Two independent panels, each listing a directory/prefix with columns Name, Ext, Size, Date; a function-key bar at the bottom (F3 View, F4 Edit, F5 Copy, F6 Move, F7 New Folder, F8 Delete, Alt+F4 Exit); keyboard-driven navigation. Copy/Move between the two panels is the core workflow.
- **Scope**: manage directories (S3 prefixes) and files (objects) on a MinIO server (S3-compatible API, not AWS S3 itself). MinIO usually needs path-style addressing; for local testing, run a MinIO container from the shared `lab-infra` stack if it has one, otherwise ask before adding one.
- **Profiles**: multiple profiles, each holding a custom endpoint URL (no AWS-only assumptions: no fixed region/endpoint resolution, path-style addressing may be needed) and its secrets.
- **Security**: profile secrets live in the app's own encrypted vault (see Vault below), not the OS keychain; a master key is required to log in (unlock) the app. An optional OS-keychain "remember on this device" is planned with a silent fallback to the master-key prompt (see `docs/implement/s3-commander-roadmap.md`).
- **S3 client**: `aws-sdk-s3`, one client per unlocked profile (endpoint URL, path-style, static credentials, checksums only when required); the bucket is passed per request, so one client serves every bucket.
- **Platforms**: macOS and Linux. The vault is plain files, so it behaves the same on both; do not make the OS keychain a hard dependency (minimal Linux setups have no Secret Service).

## Vault (implemented)

- `src-tauri/src/vault.rs` is plain Rust (no Tauri dependency, unit-tested). `lib.rs` holds a `Mutex<Vault>` in Tauri managed state and exposes thin commands: `vault_status`, `vault_create`, `vault_unlock`, `vault_lock`, `profile_list`, `profile_save`, `profile_delete`.
- File `vault.json` in the Tauri app data dir: JSON `{version, salt, nonce, ciphertext}` (base64). Master key -> Argon2id (random 16-byte salt) -> 32-byte key -> XChaCha20-Poly1305 over the whole profile list; fresh random 24-byte nonce on every save, file replaced atomically (tmp + rename).
- No stored master-key hash: a wrong key fails on the AEAD auth tag, as does a tampered file. Vault states: no file = create, file = unlock.
- The derived key lives only in the managed state (zeroized on lock/drop) and is never sent to the frontend. `profile_list` returns profiles without `secret_key`; `profile_save` with an empty secret on an existing profile keeps the stored secret. `Vault::get_profile` (with secret) is internal, for the later S3 step.
- Profile = id, name, endpoint URL, access key, secret key, region (default `us-east-1`).
- **Transfer settings**: `Profile`, `ProfileInput` and `ProfileSummary` flatten `transfer_settings::TransferFields` (four strings `multipart_threshold`, `multipart_chunksize`, `max_concurrent_requests`, `addressing_style`; `#[serde(default)]`, so vaults written before them still decrypt and load, empty = not set). Stored as normalized text (`100MB`, `8388608`, `20`, `virtual`), not bytes, so the form shows what the user typed and a bad imported value stays visible. `transfer_settings::validate_transfer` (called by `validate_profile_input`, one error per field) and `effective_transfer_settings(&profile.transfer)` (AWS CLI defaults 8 MiB / 8 MiB / 10, style `path`) are the only places that parse them; step 4 consumes the latter. `s3::client_config_builder` uses the style: `path` forces path style, `virtual`/`auto` use the SDK default. The TS mirror is `validate_profile.ts`, same `validation_cases.json`.
- **Import from AWS CLI**: `aws_config.rs` (pure, takes text or a path) parses `[default]`/`[profile x]`, comments and the nested `s3 =` block; `aws_config_list_profiles` and `aws_config_read_profile(name)` in `lib.rs` resolve `AWS_CONFIG_FILE` or `~/.aws/config` and are called only from the form button. Returns `AwsProfileSettings` (four settings, `region`, `endpoint_url`, s3-specific endpoint wins); the form fills them as a preview and marks them touched so validation flags bad values.
- **Profile validation**: `src-tauri/src/profile_rules.rs::validate_profile_input` is the one authoritative place (no Tauri dependency); `Vault::save_profile` calls it and fails with `VaultError::Validation(Vec<FieldError>)`, at most one `{field, message}` per field (`name`, `endpoint`, `access_key`, `secret_key`, `region`). `profile_save` returns `ProfileSaveError {message, fields}`; other commands are unchanged. Messages never contain the checked values. The frontend mirror is `src/profile/validate_profile.ts`; both are tested against `src/profile/validation_cases.json`. Rules: name trimmed, required, max 64, unique case-insensitively among the other profiles; endpoint trimmed, `http`/`https` only, host required, no whitespace, user info, query, fragment or path, port 1..65535, normalized to `scheme://host[:port]` (lowercase host, no trailing slash); access key trimmed, required, no whitespace or control characters; secret required on create, blank on edit keeps the stored one, never trimmed, no control characters; region trimmed, default `us-east-1`, `[a-z0-9-]` up to 32. `http://` is allowed with a non-blocking warning. Save never tests connectivity (the Test button does).

## Browse (implemented, roadmap step 2)

- `src-tauri/src/s3.rs` (no Tauri dependency): `client_config_builder(profile)` sets endpoint URL, `force_path_style(true)`, region, static credentials and `WhenRequired` request/response checksums (no `aws-config`). `list_buckets`, `list_dir(bucket, prefix, token)` return one page (delimiter `/`, prefixes become dirs, keys files, the key equal to the prefix is skipped, `next_token` for the next page), `check_connection` backs `profile_test`. SDK errors map to `AppError::S3` with a readable message.
- `src-tauri/src/local.rs`: `list_dir(path)` over `std::fs`, dirs first, hidden files included, IO errors returned as readable `AppError::Local`. An empty path means the home directory; the frontend never touches the file system.
- `src-tauri/src/app_error.rs`: `AppError` serializes to its message string. New commands return it; the older vault commands still return `String`.
- `lib.rs`: `ClientCache` (managed state) holds the client of the one active profile; it is cleared on `vault_lock`, `profile_save`, `profile_delete` and replaced when another profile is used. `profile_test` always builds a fresh client. Commands: `s3_list_buckets`, `s3_list_dir`, `local_list_dir`, `profile_test`, `profile_duplicate` (copies the secret inside the vault, returns a summary only).
- Frontend state: `src/browse/browse_store.ts` (Zustand) holds `left`/`right` panel slices (source, path, entries, nextToken, cursor, marked, scrollTop, sort), `active`, `profileId`, `buckets`. `setProfile` (on change) and `lock` reset only bucket panels; Local keeps its state. No secrets in the store. `panel_loader.ts` loads listings and drops responses that arrive after the panel moved on.
- The S3 pagination loads the next page when the cursor nears the end of the loaded rows.

- Context menu (step 3c): `context_menu.ts` (state, item list, selection rules) and `context_menu_view.tsx` (surface); handlers reuse `ops_flow` and `openRowAt` in `panel_loader.ts`.

## File operations (implemented, roadmap step 3a)

- **Planner** `src-tauri/src/transfer_plan.rs` (pure, no Tauri/SDK/fs): `Location` (local dir or bucket + prefix), `TransferRequest {source, dest, items, mode}`, `Found` entries under the selected items, `build_plan` maps names and keys for the four directions (upload, download, server copy, local copy), `check_destination` refuses same-place copies and a folder into itself, `find_conflicts`, `apply_resolutions(plan, existing, Resolutions{per_item, default})`, `auto_rename` ("name (1).ext"), `summarize`, `delete_batches` (1000). A conflict with no per-item decision and no default is an error, so nothing runs before every conflict is resolved. Directories merge and never conflict; conflicts are per file.
- **Engine** `transfer_run.rs`: expands the selection (local walk, server listing with no delimiter, folder marker `dir/` included), probes the destination (one listing per selected folder, HEAD per other file; "keep both" names are probed too), resolves, runs item by item. Move = copy, verify the destination size, then delete the source; a failed copy or verify keeps that item's source and is reported. Server sources are deleted in one batched DeleteObjects after the run; local move tries `fs::rename` first. `delete_items`, `new_folder`, `rename_item` live here too. Rename on a server is a Move inside one directory with `dest_name` (refused when the new name exists).
- **Adapters**: `s3_ops.rs` (list all, head, empty put, CopyObject, multipart UploadPartCopy above 5 GiB with abort on failure, DeleteObjects batches) and `local_ops.rs` (walk, copy tree, rename with copy fallback, New folder, delete to Trash through the `TrashBin` trait; `SystemTrash` wraps the `trash` crate, tests inject a fake).
- **File transfer**: upload and download go through the step 4a engine below; there is no per-file size limit short of S3's 5 TiB. `copy_item(client, item, mode, env, resume_upload_id)` copies one planned item and takes a `TransferEnv`; the job runner (below) builds one per item from the profile's effective settings (`transfer_settings_for` in `lib.rs`) with its own sink and cancel token. `run_transfer(client, request, resolutions, env)` is the one-shot whole-transfer path (used by rename; tests use `TransferEnv::default()`: AWS CLI defaults, no-op sink, a token nobody cancels). The UI's copy and move no longer call it, they go through `transfer_start`.
- **Commands** (thin wrappers, `profile_id` only; the client comes from the cache and is needed only when a location is a bucket): `transfer_preview`, `transfer_start` (see Transfer queue), `items_delete`, `folder_create`, `item_rename`. Results are per-item (`RunReport`, `DeleteReport`) and shown, never swallowed.
- **Frontend** `src/ops/`: `ops_targets.ts` (pure target and destination selection), `ops_store.ts` (the one open dialog, separate from panel state), `ops_flow.ts` (flows; transfers end in `startJob` = `transferStart` + `registerJob`, the dialogs close at once; refresh goes through `panel_refresh.ts`, which reuses `openPath` and keeps the cursor row), `ops_dialogs.tsx` (delete confirm, name prompt, plan summary, per-item conflict dialog with Overwrite / Skip / Keep both and the three "all" variants plus Cancel, busy and result for delete, rename and New folder). Esc cancels, Enter confirms; function keys are ignored while a dialog is open. F3 View and F4 Edit stay disabled (step 5).

## Transfer engine (implemented, roadmap step 4a; Rust only)

- **Modules** (no Tauri dependency): `part_plan.rs` (pure), `transfer_control.rs` (shared types), `multipart_upload.rs`, `ranged_download.rs`. `transfer_run::copy_item` calls `multipart_upload::upload_file` and `ranged_download::download_file`; server-to-server copy still uses `s3_ops::copy_object` (CopyObject / UploadPartCopy) unchanged.
- **Settings**: `TransferEnv {settings: EffectiveTransferSettings, sink: Arc<dyn ProgressSink>, cancel: CancelToken, retry: RetryPolicy}`. Threshold, chunk size and concurrency come from the profile through `effective_transfer_settings`; the defaults (8 MiB / 8 MiB / 10) are still unmeasured against a real MinIO.
- **Part plan**: `plan_parts(size, chunksize)`: part size = chunksize, raised to 5 MiB, raised to `ceil(size / 10,000)`, capped at 5 GiB; last part may be shorter; 0 bytes = no parts (PutObject is used); above 5 TiB = `AppError::Invalid`. Upload uses PutObject when `size < min(threshold, 5 GiB)` or the file is empty.
- **Upload**: CreateMultipartUpload, then `run_bounded` runs the missing parts with at most `upload_concurrency` in flight, then CompleteMultipartUpload with the parts sorted by number. Each part is read from the file at its offset into a buffer only while it is being sent. **Memory bound**: parts in flight x part size, and `TransferEnv::upload_concurrency(part_size)` lowers the concurrency so that product stays within `MAX_INFLIGHT_BYTES` (1 GiB); with the defaults it is 10 x 8 MiB = 80 MiB, a 5 TiB file (~524 MiB parts) runs one part at a time (slow, but 1 GiB is the cap; raise `MAX_INFLIGHT_BYTES` if that proves too conservative). Downloads hold only the SDK's current body chunk.
- **Retry** (`with_retry`): 3 attempts per part or range, wait `200 ms * 2^(n-1)`, only when `classify_sdk_error` says transient (dispatch failure, timeout, HTTP 5xx); a 4xx is final. The SDK's own retry is turned off on those requests (`single_attempt()`), so the policy is not multiplied.
- **Abort and cleanup**: a cancel calls `AbortMultipartUpload` best effort (when it fails the returned `EngineError` carries `leftover_upload_id` and its text names the id). Any other failure (a permanent part failure, CompleteMultipartUpload, a failed resume) does NOT abort: the upload is kept so the queue's Retry can resume it, and the caller already holds its id from `ProgressSink::upload_created`; `multipart_upload::abort_upload` is how the queue cleans it up later. Cancel is `EngineError::Cancelled`, never retried.
- **Resume** `resume_upload(client, env, bucket, key, path, upload_id)`: ListParts (all pages, with the part number marker), parts with the planned number and size are kept with their ETag, the rest are uploaded, then complete. Like a fresh upload it is kept on failure and aborted on cancel; when ListParts itself fails the error carries the upload id. The id of a new upload is announced through `ProgressSink::upload_created` as soon as it exists (4b needs it for Retry). Resume across app restarts is out of scope (the id is not persisted, see the leak risk below).
- **Download**: HEAD (size + ETag), then ranges of `multipart_chunksize` with `If-Match: <etag>`, one stream per file (items of a job run one after another; jobs run in parallel), appended to `<name>.part`; `<name>.part.meta` holds the ETag and size (two lines). An existing `.part` is continued from its length only when the sidecar's ETag and size equal the object's and the length does not exceed the size; otherwise it restarts. Each range attempt first cuts the file back to its offset, so a retry never duplicates bytes; a short or oversized body is an error (a short one is retried, an oversized one is not). The final length must equal the object size before the atomic rename. Cancel deletes `.part` and the sidecar; any other failure keeps both and the error says "the partial download was kept for resume".
- **Progress and cancel**: `ProgressSink` (`upload_created`, `bytes_total`, `bytes_done`, `part_done`; all default no-ops, `NoProgress` is the no-op) is fed through `ProgressTracker`, which adds under a lock so concurrent parts report non-decreasing totals ending at the object size; granularity is one part or range (resumed bytes are reported first). `CancelToken` is an `AtomicBool` plus `tokio::sync::Notify` (no new crate); it is checked before each part or range, inside waits (backoff, `run_bounded`) and while streaming a body, and `run_bounded` aborts the in-flight tasks when it flips. The queue (below) owns one token per job run and flips it on Cancel and Lock.

## Transfer queue (implemented, roadmap step 4b)

- **Why jobs**: a transfer (what F5, F6 and drag and drop start, after the plan and conflict dialogs) is a background job, not a blocking command. `transfer_start(profile_id, request, resolutions)` builds the client and the profile's effective settings, queues the job and returns its id at once; the UI never waits for the run. Delete, New folder and Rename keep their blocking dialogs.
- **State machine** `transfer_job.rs` (pure, no Tauri, no SDK, no I/O; tested incl. illegal transitions): job `queued -> running -> done | failed | cancelling -> cancelled`; a queued job cancels at once, `failed` and `cancelled` go back to `queued` on Retry, only a finished job can be dismissed. Item `pending -> running -> done | failed(message)`, `skipped` for what the conflict policy skipped. A cancel puts the running item back to `pending`; Retry puts failed items back to `pending` and keeps finished ones, so a retry never repeats finished work. `JobModel::snapshot()` (counts, bytes, current item, up to 200 failures plus `failures_total`) and `progress_event()` are the only shapes the UI sees. `job_title` builds "Upload 3 items to bucket/prefix".
- **Runner** `transfer_queue.rs` (no Tauri dependency): `TransferQueue` (cheap to clone, `Arc` inside) holds the jobs in start order; `schedule()` starts queued jobs while fewer than `MAX_RUNNING_JOBS` (3) run (cancelling counts as running); each job is one tokio task. The task builds the plan first (`transfer_run::prepare_plan`: expand, probe, conflict decisions; a failure there fails the job with a message and Retry prepares again), then runs the items one after another through the `ItemRunner` trait (production `EngineRunner` calls `transfer_run::copy_item`; tests script it). Move = copy, verify size, then delete: local sources are removed inside `copy_item`, server sources are collected per bucket and deleted in one batched DeleteObjects at the end of each run, only for items that succeeded; a refused key is reported as a job failure and tried again after Retry. Emptied local source folders are removed at the end of a run that was not cancelled.
- **Events** through the `EventSink` trait (`lib.rs` implements it with `app.emit`; tests record): `transfer://state` carries a `JobSnapshot` on every job state change and item failure; `transfer://progress` carries `ProgressEvent` (job id, current item name, item bytes done/total, job bytes done/total, item index and count), throttled by `ProgressThrottle` to one per 100 ms per job; the first event of an item and the complete event at its end are always sent. Payloads hold titles, item names (paths or bucket/key), counts and readable error messages only, never credentials, signed URLs or the secret key (a test serializes every event of a failing upload and checks it). `transfer_list` returns the snapshots so a page that attaches late (or reloads) can seed itself.
- **Retry resumes**: the engine no longer aborts a multipart upload on a non-cancel failure. The runner records the id announced by `ProgressSink::upload_created` (or the resumed id) per item in the job's memory; Retry runs that item through `resume_upload` with the id (ListParts, only missing parts are sent). A resume whose upload no longer exists on the server (expired or aborted elsewhere) fails again with the server's message; Dismiss the job and start a new one. Cancel, Dismiss and Lock abort every kept upload of the job; an abort that fails is reported in the item message ("could not abort the incomplete upload <id> ... it may remain on the server") and a Dismiss returns that text as an error while still forgetting the job. Downloads resume from their `.part` file as in 4a.
- **Cancel**: running job -> `cancelling`, the job's `CancelToken` flips, the engine stops at the next part or range and aborts its own upload, the task then aborts what the job kept, flushes the removals of items that did finish and settles in `cancelled`. Non-cancellable work: a local copy (`tokio::fs::copy`) finishes the file it is on.
- **Lock** (`vault_lock`, now async): `TransferQueue::shutdown` cancels every job, waits for the tasks, aborts every kept upload and forgets all jobs; the client cache is cleared after that. The frontend clears its queue store.
- **Leak risk (known, accepted for 4b)**: the kept upload id lives only in memory. If the app crashes or is quit while a failed job still holds a multipart upload (or while an upload is in flight and the process dies), the incomplete upload stays on the server and its parts keep using storage until it is aborted. There is no startup scan. A "clean up incomplete uploads" tool (ListMultipartUploads + Abort) or a bucket lifecycle rule (`AbortIncompleteMultipartUpload`) is the later fix; neither exists yet.
- **Frontend** `src/queue/`: `queue_logic.ts` (pure, tested: types mirroring the Rust snapshots, `applyStateEvent` / `applyProgressEvent` reducers, `speedOf` over a 5 s window of samples, `etaSeconds`, `statusText`, `buttonsFor`), `queue_store.ts` (Zustand: jobs, `expanded`, `meta` = where each job was going, `refreshed`), `queue_events.ts` (`attachQueueEvents` listens to both events with `@tauri-apps/api/event` `listen`, seeds from `transfer_list`, returns the unlisten function; `registerJob(jobId, meta)` is called by the flows), `queue_api.ts`, `queue_panel.tsx`. `App.tsx` attaches the listeners while the vault is unlocked (also on the Profiles screen, so no event is lost) and clears the store on Lock. When a job reaches `done`, `failed` or `cancelled`, the panels currently showing its destination (and, for a move, its source) are refreshed with `refreshPanel` (`openPath`, cursor row kept), once per finished state (a retried job refreshes again); a panel the user navigated away from is left alone, and a job that finished before the flow registered its id is refreshed at registration. Marks of the source panel are cleared when the job starts, so marks made later are not wiped when an earlier job ends.

## Drag and drop (implemented, roadmap step 3b)

- **Why pointer events**: the in-app drag uses `pointerdown` / `pointermove` / `pointerup` on window, not the HTML5 `draggable` API. HTML5 DnD inside the Tauri webview is unreliable across WebKit and WebKitGTK and conflicts with Tauri's native drag-drop handler (which stays enabled to receive OS drops). A press becomes a drag after 4 px of movement; a press that never moves stays a plain click (the click is only swallowed after a real drag).
- `src/browse/drag_drop_logic.ts` (pure, tested): threshold, `dragSet` (marked rows if the dragged row is marked, else just it, never ".."), `hitTest` / `targetFromElement` (rows carry `data-row-name`, `data-row-dir`, `data-row-up`; the panel root carries `data-panel`; rows are identified by name, so sorting does not matter), `resolveDrop` (destination, copy vs move, all refusals), `autoScrollStep`. `drop_locations.ts` holds the location helpers.
- `drag_drop.ts`: the controller (module state + a small Zustand store for the ghost, hover cue and toast). `panelDragProps(side)` and `useDropHighlight(side)` are the only hooks `file_panel.tsx` uses. A drop calls `startTransferOf(operation, mode)` in `ops_flow.ts`, the same planning path as F5/F6 (plan summary, per-item conflicts, then a queued job); no operation logic is duplicated.
- Rules: plain drop = copy, Shift = move; same panel = move into a folder row only; Esc cancels; refusals show a toast and run nothing.
- **OS drop path** (`os_drop.ts`): `getCurrentWebview().onDragDropEvent` gives absolute paths and a physical-pixel position relative to the webview. The position is divided by `devicePixelRatio` and hit-tested to a panel and folder row. Only a server panel accepts it; a Local panel or a panel without a source is ignored with a message. `local_stat_paths` (Rust, `local.rs`) tells folders from files and splits parent and name; all paths must share one parent (items are relative to a source directory), then the upload runs as a copy through `startTransferOf`. The event is enabled by `dragDropEnabled: true` on the window in `tauri.conf.json` (it is the default; set explicitly). Dragging out of the app is not supported.

## Presigned URLs (implemented, roadmap step 3d)

- `src-tauri/src/presign.rs` (no Tauri dependency): SigV4 query signing through `aws-sdk-s3` `PresigningConfig` with the profile's static credentials; a local computation, no request is sent. The URL uses the client's endpoint and path-style addressing. `expiry_duration` allows 1 second to 604800 (7 days) and rejects the rest with `AppError::Invalid`; `content_disposition` builds `attachment; filename="<ascii fallback>"; filename*=UTF-8''<percent-encoded>` and rejects empty names and control characters; `presign_get` (one key), `presign_keys` (batch, order kept, a failing key is a per-item `error`), `expand_targets` (files as they are, folders through `s3_ops::list_all`, zero-byte `dir/` markers skipped, cut at `MAX_URLS` = 1000 with the full `total` reported), `presign_selection` and `preview_selection` (object count before generating). `start` time is a parameter so tests are deterministic.
- Commands (thin): `presign_preview(profile_id, bucket, items)`, `presign_urls(profile_id, bucket, items, expires_secs, download_filename?)` returning `{items: [{key, name, url|null, expires_at|null, error|null}], total, capped}`, `write_text_file(path, contents)` (`text_file.rs`; absolute path only, creates or truncates that one file). Items are `{key, is_dir}` with full keys; a folder key ends with `/`. A download file name is refused when the selection expands to more than one object.
- Frontend: `presignSelection` (ops_targets.ts) is the one selection rule for F9 and the menu entry (server panel, marked items else cursor item, never `..`). `presign_flow.ts` drives the dialogs kept in `ops_store` (`presign-options`, `presign-confirm` for a folder, `presign-result`); the F-key and the context menu both call `startPresign`. Copy uses `clipboard.ts` (Clipboard API, then textarea select + `execCommand("copy")`), results show in `toast.tsx`. Save as text file picks the path with `tauri-plugin-dialog` `save()` (capability `dialog:allow-save`) and writes through `write_text_file`.
