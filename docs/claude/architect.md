# Architecture

Design from the project owner; the vault, browsing (step 2), its dual-pane UI and the basic file operations (step 3a) are implemented; drag and drop, the context menu, large transfers and view/edit are not yet.

- **Shell**: Tauri desktop app (Rust backend + web frontend).
- **UI**: Total Commander-style dual pane. Two independent panels, each listing a directory/prefix with columns Name, Ext, Size, Date; a function-key bar at the bottom (F3 View, F4 Edit, F5 Copy, F6 Move, F7 New Folder, F8 Delete, Alt+F4 Exit); keyboard-driven navigation. Copy/Move between the two panels is the core workflow.
- **Scope**: manage directories (S3 prefixes) and files (objects) on a MinIO server (S3-compatible API, not AWS S3 itself). MinIO usually needs path-style addressing; for local testing, run a MinIO container from the shared `lab-infra` stack if it has one, otherwise ask before adding one.
- **Profiles**: multiple profiles, each holding a custom endpoint URL (no AWS-only assumptions: no fixed region/endpoint resolution, path-style addressing may be needed) and its secrets.
- **Security**: profile secrets live in the app's own encrypted vault (see Vault below), not the OS keychain; a master key is required to log in (unlock) the app. An optional OS-keychain "remember on this device" is planned with a silent fallback to the master-key prompt (see `docs/implement/s3-commander-roadmap.md`).
- **S3 client**: `aws-sdk-s3`, one client per unlocked profile (endpoint URL, path-style, static credentials, checksums only when required); the bucket is passed per request, so one client serves every bucket.
- **Platforms**: macOS and Linux. The vault is plain files, so it behaves the same on both; do not make the OS keychain a hard dependency (minimal Linux setups have no Secret Service).

## Vault (implemented)

- `src-tauri/src/vault.rs` is plain Rust (no Tauri dependency, unit-tested). `lib.rs` holds a `Mutex<Vault>` in Tauri managed state and exposes thin commands: `vault_status`, `vault_create`, `vault_unlock`, `vault_lock`, `profile_list`, `profile_save`, `profile_delete`.
- File `vault.json` in the Tauri app data dir: JSON `{version, salt, nonce, ciphertext}` (base64). Master key -> Argon2id (random 16-byte salt) -> 32-byte key -> XChaCha20-Poly1305 over the whole profile list; fresh random 24-byte nonce on every save, file replaced atomically (tmp + rename).
- No stored master-key hash: a wrong key fails on the AEAD auth tag, as does a tampered file. Vault states: no file = create, file = unlock.
- The derived key lives only in the managed state (zeroized on lock/drop) and is never sent to the frontend. `profile_list` returns profiles without `secret_key`; `profile_save` with an empty secret on an existing profile keeps the stored secret. `Vault::get_profile` (with secret) is internal, for the later S3 step.
- Profile = id, name, endpoint URL, access key, secret key, region (default `us-east-1`).
- **Transfer settings**: `Profile`, `ProfileInput` and `ProfileSummary` flatten `transfer_settings::TransferFields` (four strings `multipart_threshold`, `multipart_chunksize`, `max_concurrent_requests`, `addressing_style`; `#[serde(default)]`, so vaults written before them still decrypt and load, empty = not set). Stored as normalized text (`100MB`, `8388608`, `20`, `virtual`), not bytes, so the form shows what the user typed and a bad imported value stays visible. `transfer_settings::validate_transfer` (called by `validate_profile_input`, one error per field) and `effective_transfer_settings(&profile.transfer)` (AWS CLI defaults 8 MiB / 8 MiB / 10, style `path`) are the only places that parse them; step 4 consumes the latter. `s3::client_config_builder` uses the style: `path` forces path style, `virtual`/`auto` use the SDK default. The TS mirror is `validate_profile.ts`, same `validation_cases.json`.
- **Import from AWS CLI**: `aws_config.rs` (pure, takes text or a path) parses `[default]`/`[profile x]`, comments and the nested `s3 =` block; `aws_config_list_profiles` and `aws_config_read_profile(name)` in `lib.rs` resolve `AWS_CONFIG_FILE` or `~/.aws/config` and are called only from the form button. Returns `AwsProfileSettings` (four settings, `region`, `endpoint_url`, s3-specific endpoint wins); the form fills them as a preview and marks them touched so validation flags bad values.
- **Profile validation**: `src-tauri/src/profile_rules.rs::validate_profile_input` is the one authoritative place (no Tauri dependency); `Vault::save_profile` calls it and fails with `VaultError::Validation(Vec<FieldError>)`, at most one `{field, message}` per field (`name`, `endpoint`, `access_key`, `secret_key`, `region`). `profile_save` returns `ProfileSaveError {message, fields}`; other commands are unchanged. Messages never contain the checked values. The frontend mirror is `src/profile/validate_profile.ts`; both are tested against `src/profile/validation_cases.json`. Rules: name trimmed, required, max 64, unique case-insensitively among the other profiles; endpoint trimmed, `http`/`https` only, host required, no whitespace, user info, query, fragment or path, port 1..65535, normalized to `scheme://host[:port]` (lowercase host, no trailing slash); access key trimmed, required, no whitespace or control characters; secret required on create, blank on edit keeps the stored one, never trimmed, no control characters; region trimmed, default `us-east-1`, `[a-z0-9-]` up to 32. `http://` is allowed with a non-blocking warning. Save never tests connectivity (the Test button does).

## Browse (implemented, roadmap step 2)

- `src-tauri/src/s3.rs` (no Tauri dependency): `client_config_builder(profile)` sets endpoint URL, `force_path_style(true)`, region, static credentials and `WhenRequired` request/response checksums (no `aws-config`). `list_buckets`, `list_dir(bucket, prefix, token)` return one page (delimiter `/`, prefixes become dirs, keys files, the key equal to the prefix is skipped, `next_token` for the next page), `check_connection` backs `profile_test`. SDK errors map to `AppError::S3` with a readable message.
- `src-tauri/src/local.rs`: `list_dir(path)` over `std::fs`, dirs first, hidden files included, IO errors returned as readable `AppError::Local`. An empty path means the home directory; the frontend never touches the file system.
- `src-tauri/src/app_error.rs`: `AppError` serializes to its message string. New commands return it; the older vault commands still return `String`.
- `lib.rs`: `ClientCache` (managed state) holds the client of the one active profile; it is cleared on `vault_lock`, `profile_save`, `profile_delete` and replaced when another profile is used. `profile_test` always builds a fresh client. Commands: `s3_list_buckets`, `s3_list_dir`, `local_list_dir`, `profile_test`, `profile_duplicate` (copies the secret inside the vault, returns a summary only).
- Frontend state: `src/browse/browse_store.ts` (Zustand) holds `left`/`right` panel slices (source, path, entries, nextToken, cursor, marked, scrollTop, sort), `active`, `profileId`, `buckets`. `setProfile` (on change) and `lock` reset only bucket panels; Local keeps its state. No secrets in the store. `panel_loader.ts` loads listings and drops responses that arrive after the panel moved on.
- The S3 pagination loads the next page when the cursor nears the end of the loaded rows.

- Context menu (step 3c): `context_menu.ts` (state, item list, selection rules) and `context_menu_view.tsx` (surface); handlers reuse `ops_flow` and `openRowAt` in `panel_loader.ts`.

## File operations (implemented, roadmap step 3a)

- **Planner** `src-tauri/src/transfer_plan.rs` (pure, no Tauri/SDK/fs): `Location` (local dir or bucket + prefix), `TransferRequest {source, dest, items, mode}`, `Found` entries under the selected items, `build_plan` maps names and keys for the four directions (upload, download, server copy, local copy), `check_destination` refuses same-place copies and a folder into itself, `find_conflicts`, `apply_resolutions(plan, existing, Resolutions{per_item, default})`, `auto_rename` ("name (1).ext"), `summarize`, `delete_batches` (1000). A conflict with no per-item decision and no default is an error, so nothing runs before every conflict is resolved. Directories merge and never conflict; conflicts are per file.
- **Engine** `transfer_run.rs`: expands the selection (local walk, server listing with no delimiter, folder marker `dir/` included), probes the destination (one listing per selected folder, HEAD per other file; "keep both" names are probed too), resolves, runs item by item. Move = copy, verify the destination size, then delete the source; a failed copy or verify keeps that item's source and is reported. Server sources are deleted in one batched DeleteObjects after the run; local move tries `fs::rename` first. `delete_items`, `new_folder`, `rename_item` live here too. Rename on a server is a Move inside one directory with `dest_name` (refused when the new name exists).
- **Adapters**: `s3_ops.rs` (list all, head, put, get, CopyObject, multipart UploadPartCopy above 5 GiB with abort on failure, DeleteObjects batches) and `local_ops.rs` (walk, copy tree, rename with copy fallback, New folder, delete to Trash through the `TrashBin` trait; `SystemTrash` wraps the `trash` crate, tests inject a fake).
- **Limit (step 4)**: upload (one PutObject) and download (one GetObject to a temp file, then rename) are capped at 5 GiB per file; larger files fail with a clear per-item error. No multipart upload, progress, cancel or resume.
- **Commands** (thin wrappers, `profile_id` only; the client comes from the cache and is needed only when a location is a bucket): `transfer_preview`, `transfer_execute`, `items_delete`, `folder_create`, `item_rename`. Results are per-item (`RunReport`, `DeleteReport`) and shown, never swallowed.
- **Frontend** `src/ops/`: `ops_targets.ts` (pure target and destination selection), `ops_store.ts` (the one open dialog, separate from panel state), `ops_flow.ts` (flows; refresh reuses `openPath`, clears marks, keeps the cursor row), `ops_dialogs.tsx` (delete confirm, name prompt, plan summary, per-item conflict dialog with Overwrite / Skip / Keep both and the three "all" variants plus Cancel, busy, result). Esc cancels, Enter confirms; function keys are ignored while a dialog is open. F3 View and F4 Edit stay disabled (step 5).

## Drag and drop (implemented, roadmap step 3b)

- **Why pointer events**: the in-app drag uses `pointerdown` / `pointermove` / `pointerup` on window, not the HTML5 `draggable` API. HTML5 DnD inside the Tauri webview is unreliable across WebKit and WebKitGTK and conflicts with Tauri's native drag-drop handler (which stays enabled to receive OS drops). A press becomes a drag after 4 px of movement; a press that never moves stays a plain click (the click is only swallowed after a real drag).
- `src/browse/drag_drop_logic.ts` (pure, tested): threshold, `dragSet` (marked rows if the dragged row is marked, else just it, never ".."), `hitTest` / `targetFromElement` (rows carry `data-row-name`, `data-row-dir`, `data-row-up`; the panel root carries `data-panel`; rows are identified by name, so sorting does not matter), `resolveDrop` (destination, copy vs move, all refusals), `autoScrollStep`. `drop_locations.ts` holds the location helpers.
- `drag_drop.ts`: the controller (module state + a small Zustand store for the ghost, hover cue and toast). `panelDragProps(side)` and `useDropHighlight(side)` are the only hooks `file_panel.tsx` uses. A drop calls `startTransferOf(operation, mode)` in `ops_flow.ts`, the same planning path as F5/F6 (plan summary, per-item conflicts, busy, result, refresh); no operation logic is duplicated.
- Rules: plain drop = copy, Shift = move; same panel = move into a folder row only; Esc cancels; refusals show a toast and run nothing.
- **OS drop path** (`os_drop.ts`): `getCurrentWebview().onDragDropEvent` gives absolute paths and a physical-pixel position relative to the webview. The position is divided by `devicePixelRatio` and hit-tested to a panel and folder row. Only a server panel accepts it; a Local panel or a panel without a source is ignored with a message. `local_stat_paths` (Rust, `local.rs`) tells folders from files and splits parent and name; all paths must share one parent (items are relative to a source directory), then the upload runs as a copy through `startTransferOf`. The event is enabled by `dragDropEnabled: true` on the window in `tauri.conf.json` (it is the default; set explicitly). Dragging out of the app is not supported.
