# Safety

- Profile secrets are stored only encrypted in the app vault (master-key derived key); never write them to plain config files, logs, or git. The master key is never persisted in plain text.
- Real credentials, bucket names tied to real environments, and endpoints stay out of tracked files (see global "Secrets & Infra Hygiene").
- Testing against real S3 buckets: Delete/Move (F6/F8) are destructive. Use a throwaway bucket or prefix and confirm the target with the user before running anything that writes or deletes remotely.
- The vault file holds only ciphertext; losing the master key means the profiles are unrecoverable (no reset path by design). Frontend commands never return `secret_key`, and the master key is passed per call and not stored or logged.
- Vault tests use tempdirs and touch no network or database.
- AWS CLI import: `aws_config.rs` returns a fixed struct of six non-secret fields; a test proves access key, secret and token lines in the config never come back. The credentials file is never opened.
- AWS CLI import (profile form) reads only the non-secret keys listed in the roadmap from `~/.aws/config`, only when the user clicks Import; it never reads `~/.aws/credentials` or any key/secret/token value, and tests never read the real home directory.
- Presigned URLs are credential-like: anyone holding one can read the object until it expires, and the URL points at the profile endpoint. They are never logged (Rust or frontend), never stored in the vault, the panel store or localStorage; they live only in the open `presign-result` dialog state, which is cleared on close and when the screen unmounts (Lock). Errors and URLs never contain the secret key (SigV4 puts only the access key id in the URL; a test asserts the secret is absent). Expiry is limited to 1 second to 7 days. "Save as text file" writes live signed URLs to disk, so the dialog warns about it; the user chooses the path in the native save dialog and `write_text_file` only creates or truncates that one absolute path. Tests use fake credentials and example hosts only.
- Transfer queue (4b): `transfer://state` and `transfer://progress` payloads carry only titles, item names, counts and readable error messages; never credentials, signed URLs or the secret key, and Rust tests serialize every event of a failing upload and check this. The kept multipart upload id lives only in the job's in-memory state (never in events beyond the error text of a failed abort, never in the vault or localStorage). Known leak risk: a crash or quit while a job holds a kept upload leaves an incomplete multipart upload (and its stored parts) on the server; Cancel, Dismiss and Lock abort them, a failed abort is shown in the item message. A move deletes a source only for items that succeeded and verified; a refused source delete is shown as a job failure. Testing against a real bucket: use a throwaway bucket and check ListMultipartUploads afterwards.
- Saving from the viewer overwrites user data, so every save has guards: local saves are atomic (temp file in the same folder, then rename; permissions kept) and compare size and modified time with what was opened, server saves compare the ETag (HEAD, plus `If-Match` on the PUT); a mismatch writes nothing and asks Overwrite, Save as copy or Cancel (Cancel is the focused button). Save as copy never replaces an existing server object (`create_only`). Closing with unsaved changes asks Save, Discard or Cancel. Invalid JSON is saved only after a warning. Files are opened only up to 5 MiB, UTF-8 without NUL bytes. File content is never logged, never put into error messages and never persisted; the session is cleared on close and on Lock. Tests use tempdirs and mocked S3 only, and never touch real user files. Not exercised against a real MinIO: whether the server honors `If-Match` on PutObject (the HEAD comparison covers a server that ignores it, with a small race window).
- Vault hardening (6a). What each part protects: the unlock throttle slows guessing through the app UI only (1 s doubling to 5 minutes between attempts, state in a plain file in the app data dir, so someone with file access can delete it; it is not a security boundary). Guessing against a copied `vault.json` is not slowed by it; that is what the Argon2id cost is for: new vaults and upgraded ones use 256 MiB, 4 passes, 1 lane. Measured on one Apple M1 Pro (dev build with argon2 at opt-level 3): about 0.5 s per derivation (5 runs, 0.50 to 0.55 s) versus about 15 ms for the old 19 MiB, 2 pass parameters; not measured: release build, slower machines, Linux. The vault is still one file under one master key, so a weak master key stays guessable offline. Header parameters are read from the file, so they are bounded (1 GiB, 16 passes, 8 lanes) to stop a tampered file from exhausting memory; lowering them in the header only makes decryption fail, because the key derived from them differs. The in-place upgrade never leaves a half-written vault: temp file in the same directory, verified by decrypting it again, atomic rename; a failure keeps the old file. Auto-lock cancels running transfers (as Lock does) and keeps unsaved viewer edits in memory, in the webview heap, until unlock; those edits are file text, not credentials, and nothing from the browser is rendered on the lock screen.
- Zeroizing, honestly: protected are the derived key (`Zeroizing<[u8; 32]>`), the decrypted vault plaintext buffer, the master key string inside the `vault_create` and `vault_unlock` calls (wrapped in `Zeroizing`, moved not copied) and Argon2's memory blocks (`zeroize` feature). Not protected: the master key as received over IPC (Tauri's JSON deserializer and the webview's IPC layer make copies we cannot wipe), the JS string and the input element in the webview (immutable strings are only freed by GC), decoded `Profile` values (access and secret keys are plain `String`s while unlocked) and any OS swap or core dump that captured them. Lock drops the key and profiles but cannot overwrite JS memory.
