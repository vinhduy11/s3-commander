Profiles with master-key vault (step 1)

Specs

Multi-profile support (id, name, MinIO endpoint, access key, secret key, region default us-east-1) stored in an encrypted vault unlocked by a master key. Commands: vault_status, vault_create, vault_unlock, vault_lock, profile_list, profile_save, profile_delete. Profile commands fail when locked; the key never leaves Rust; profile_list omits the secret key. No S3 calls yet.

Actions

  • Added src-tauri/src/vault.rs (Argon2id + XChaCha20-Poly1305, random salt and per-save nonce, atomic file replace, zeroized key) with 10 unit tests written first (red, then green).
  • Added thin Tauri commands and managed Mutex<Vault> in lib.rs; removed the template greet command.
  • Replaced App.tsx with a master-key screen and a profile list/form with Lock.
  • Deps: argon2, chacha20poly1305, rand, zeroize, base64, thiserror, tempfile (dev). Updated README, CHANGELOG, architect and safety docs.

Tradeoffs

  • Own vault file instead of the OS keychain: no extra service and identical behaviour on all platforms, but the user must remember the master key (no recovery).
  • Whole list encrypted as one blob: simple and one auth tag; every save re-encrypts everything, fine for a handful of profiles.
  • Argon2 default parameters (19 MiB, 2 passes): reasonable for a desktop app; not tuned or measured for slow machines.
  • Master key crosses the IPC boundary as a string per call; it is not stored, but the string in the webview/Rust heap is not zeroized (inferred limitation).
  • No auto-lock timer or brute-force throttling yet (YAGNI for step 1).
