Endpoint error detail (2026-11-26)

Specs

Measured by the owner: after adding a profile with an https MinIO endpoint the app only showed "cannot reach the endpoint (check the URL and the network)". That text was produced for every SdkError::DispatchFailure (DNS, refused, timeout, TLS, bad URL, proxy), so the real cause was hidden. The root cause of the owner's failure is not known; a TLS certificate problem is only a suspect.

Required: the message says why, with a trimmed root-cause string, never credentials; the old hint stays only for an unclassified failure; no change to TLS trust behavior; no frontend, vault or transfer change.

Actions

  • src-tauri/src/s3.rs: new describe_dispatch_failure (uses DispatchFailure::is_timeout/is_user/is_io, as_connector_error() and the std::error::Error::source chain) and trim_root_cause (whitespace collapsed, 200 chars). map_sdk_error calls it for DispatchFailure.
  • Messages: could not resolve the host (DNS); connection refused; connection timed out; TLS certificate not trusted or invalid (hint: self-signed or internal CA); invalid endpoint URL; connection failed (io, unknown cause); fallback old hint. Each is followed by : <root cause> when the chain has one.
  • src-tauri/Cargo.toml: aws-smithy-runtime-api moved from dev-dependencies to dependencies (already in the lock; needed for the DispatchFailure type).
  • Tests (written first, red 6 failed / 2 passed, then green 37 passed): DNS, refused, timeout, four certificate texts, invalid URI, unclassified fallback, source-chain walk, trimming. Failures are built with SdkError::dispatch_failure(ConnectorError::io/timeout/user/other(..)).
  • .gitignore: .claude/worktrees/. CHANGELOG.md: Unreleased / Changed.

Tradeoffs

  • Classification is by the SDK kind first, then keyword match on the lower-cased source chain text (rustls and hyper give no typed variants through the boxed error). Keywords can drift with library versions; unknown text lands in "connection failed: root" which still shows the root cause. Inferred (not run against a real server): the exact wording the owner's failure will produce.
  • The "timed out" and "invalid URL" checks run before the certificate check, so a text containing both reports the earlier one.
  • Only connector error text is used, never the request, so signed headers and keys cannot appear.

TLS trust store finding (measured)

The client is the SDK default: aws-sdk-s3 default features (rustls, default-https-client), no custom http_client in src-tauri/src/s3.rs. Cargo.lock has rustls 0.23 with aws-lc, rustls-native-certs and security-framework, and has no webpki-roots, rustls-platform-verifier or native-tls. In aws-smithy-http-client 1.1.13 the default TrustStore has enable_native_roots: true and loads roots with rustls_native_certs::load_native_certs(). So the trust roots are the OS store (macOS Keychain, Linux system CA bundle, SSL_CERT_FILE, SSL_CERT_DIR). An internal CA that the OS trusts is therefore expected to be accepted (inferred, not exercised with a handshake). A cert from a CA that is not in the OS store, an incomplete chain, an expired cert or a name/IP not in the cert SAN would still be rejected.

Proposed, not implemented

  • Per-profile optional CA PEM file path, added to the trust store through http_client(...) on client_config_builder (TrustStore::default().with_pem_certificate(..)).
  • No "accept invalid certs" switch.

Not exercised

No real endpoint, no real TLS handshake, no owner server; unit tests use constructed SDK errors only.
