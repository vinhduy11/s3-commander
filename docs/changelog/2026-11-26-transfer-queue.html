Transfer queue: background jobs, events, queue panel, Cancel and Retry

Specs

Roadmap step 4b on top of the merged 4a engine. A copy, move or drop (after the plan and conflict dialogs) becomes a background job instead of a blocking command: transfer_start returns a job id at once, up to 3 jobs run at the same time, the items of a job run one after another, and the UI follows through the events transfer://state and transfer://progress (about 10 per second per job). A queue panel docked above the F-key bar shows a one-line status and, expanded, one row per job with progress, speed, ETA, item counts, Cancel, Retry, Dismiss and the per-item failures. Retry must resume: the engine keeps a failed multipart upload and Retry continues it through ListParts; Cancel, Dismiss and Lock abort it. A move deletes the source only of items that succeeded. Out of scope: View/Edit, sorting, column resizing, persisting the queue, bandwidth limits, cleaning up orphaned uploads.

Tradeoffs

  • Keep the upload on failure (leak risk). Chosen so Retry can resume. Cost: the upload id is only in memory, so a crash or quit leaves an incomplete multipart upload and its stored parts on the server. Nothing persists the id and there is no startup scan; a cleanup tool or a bucket lifecycle rule (AbortIncompleteMultipartUpload) is the later fix. A resume against an upload the server has already dropped fails with the server's message; the user dismisses the job and starts again.
  • Server move removals are batched at the end of each run (one DeleteObjects per bucket) instead of per item: cheaper, and Retry re-attempts refused keys. A cancelled or crashed run between copy and flush leaves copied sources undeleted (safe direction).
  • Marks are cleared when the job starts, not when it ends. The spec said "as before"; before, the transfer blocked the UI so the two moments coincided. Clearing at the end would wipe marks the user made while the job runs.
  • Refresh by location, not by side. The panels that currently show the job's destination (or the source of a move) are refreshed; a panel the user navigated away from is left alone.
  • Items of one job are sequential, jobs run in parallel (3). Parts are already parallel inside the engine, so a job of many small files is throughput-bound by per-item latency; per-item parallelism was not asked for.
  • Plan is built inside the job (so transfer_start returns at once even for a big folder). A planning failure shows as a failed job with a message; Retry plans again.
  • The item runner is a trait so scheduling, cancel and Retry are tested without timing tricks; the real engine paths are tested with mocked S3 clients through the same queue.
  • Dismiss of a job whose abort failed forgets the job and returns the error text (with the upload id) which the UI shows as a toast; keeping the job would make it undismissable.
  • A local copy cannot be cancelled mid-file (tokio::fs::copy); it stops after the file it is on.

Measured and inferred

Measured: cargo test (234 passed, run alone and five more times for the transfer tests, no flake), cargo check with zero warnings, npm test (360 passed), npm run build, and Chromium screenshots of the queue panel against a mocked __TAURI_INTERNALS__ that emits the events (idle, running with two jobs, collapsed status, a failed job with Retry and its failure list, a finished job; light and dark).

Inferred, not exercised: behaviour against a real MinIO; real large or long transfers (speed and ETA are tested as pure functions only); real network failures and the engine's retry timing; the real Tauri window and its event channel (the mock emits through the same callback path listen uses, but the Rust app.emit side was only compiled, not run); WebKit rendering (screenshots are Chromium); the throughput of the event stream under many tiny files; a crash leaving an incomplete upload (described, not reproduced).
