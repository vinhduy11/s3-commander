Multipart transfer engine (roadmap step 4a, Rust only)

Specs

  • Upload: PutObject below the profile's multipart_threshold, otherwise multipart with up to max_concurrent_requests parts in flight; part size = multipart_chunksize, raised to 5 MiB and to fit 10,000 parts, at most 5 GiB per part, object at most 5 TiB. Per-part retry (3 attempts, exponential backoff, transient errors only). Abort on permanent failure or cancel, reporting a failed abort with the upload id.
  • Resume of a partly uploaded multipart through ListParts (paginated); the upload id is exposed as soon as it exists. Resume across app restarts is out of scope.
  • Download: ranged GetObject into <name>.part plus an ETag/size sidecar, resumed only when both still match, size verified, atomic rename; cancel cleans up, failure keeps the temp file and says so.
  • Hooks for step 4b: ProgressSink trait (no-op implementation) and a cancel token checked between parts and ranges.
  • Wire into the 3a engine (transfer_run), remove the 5 GiB limit and too_large handling, keep the 5 TiB check. Server-to-server copy unchanged. Out of scope: queue UI, Tauri events, Cancel and Retry buttons (4b).

Large files are sparse, nothing multi-GB is written.

Tradeoffs

  • Measured: the 201 tests above, with mocked S3 (aws-smithy-mocks), temp dirs and sparse files; the SDK's own retry (3 attempts, visible as 9 calls in the first red-to-green run) multiplied the engine's retry, so it is now switched off on part, range and list requests (single_attempt()).
  • Inferred, not measured: part size, threshold and concurrency come from the profile settings (AWS CLI defaults 8 MiB / 8 MiB / 10) and are still unmeasured against a real MinIO; the memory figures (10 x 8 MiB = 80 MiB with the defaults) come from the code, not from a profiler.
  • Memory cap: parts are read into memory while sent, so the in-flight bytes are capped at 1 GiB by lowering the concurrency; chosen over streaming each part from the file (which would need a replayable, length-known body per part and is harder to retry). Cost: with ~524 MiB parts (a 5 TiB file) only one part is in flight.
  • Abort on failure also for resume: as specified, a failed resume aborts the upload, so its uploaded parts are discarded; only a failed ListParts or a failed abort leaves an id behind (reported in the error). If 4b wants Retry to resume after a failure, it needs an option to skip the abort; deliberately not added now.
  • Granularity: progress and cancel are per part / range plus a check on every body chunk of a download; an in-flight upload part is aborted by dropping its task, not drained.
  • Cancel token: AtomicBool + tokio::sync::Notify instead of tokio_util: no new crate, only tokio feature flags.
  • If-Match on every range: a changed object fails the range with a 412 (not retried) instead of mixing two versions; the temp file is kept and the next run restarts because the ETag no longer matches. Costs one extra HEAD per download.
  • Frontend untouched: too_large_count is still declared in ops_api.ts and shown in ops_dialogs.tsx; the field is no longer sent, so the notice never shows. Remove it in 4b.
  • Not exercised: real MinIO, real large files, real network failures (resets, timeouts, 5xx from a live server), the Tauri window, tauri dev, any frontend test run.
