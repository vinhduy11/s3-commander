Panel stuck on "Loading..." fix

Specs

On a fresh launch the left Local panel could stay on "Loading..." forever; re-selecting the source fixed it. Seen in browser runs with mocked Tauri commands.

Actions

  • Measured: new src/browse/panel_loader.test.ts (6 tests). Before the fix 3 failed: Local listing and Local error lost when setProfile changes profileId while the request is in flight (panel left with loading=true), and a bucket source with no profile left loading=true. Confirms the hypothesis in openPath (isCurrent() compared profileId for Local too).
  • Fix in openPath (src/browse/panel_loader.ts, the one shared place for openSource, enterDir, goUp): profile check only for bucket sources; the no-profile bucket guard runs before setLoading(true); a dropped response clears loading when its ticket is still the latest.
  • Measured: bucket responses dropped by a profile change did not leave loading=true even before the fix, because setProfile resets bucket panels; kept as regression tests. A superseded request still keeps loading for the newer one (test).
  • Measured: npm test 22 passed, npm run build ok.

Tradeoffs

  • The dropStale guard is a safety net, not needed by any currently measured path other than via the ticket check; kept small so future drop reasons cannot strand the spinner.
  • loadMore not changed: bucket only, and every drop reason resets the panel. Inferred from reading the store, no test.
  • Inferred, not exercised: timing in the real Tauri window (the race needs profile_list to resolve before local_list_dir); only mocked promises were used.
